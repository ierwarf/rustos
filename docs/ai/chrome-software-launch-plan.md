# Chrome 소프트웨어 렌더링 구현 계획

기준: `b554cdb5`, Chrome 157 (초기 게스트 진단 기준; 최신 진행 상태는 [Session Handoff](session-handoff.md) 참조). 초기 게스트 진단에서 기본 FAT 프로필은 `SingletonLock` 생성 실패로, TmpFs 프로필은 Qt Wayland 플러그인 누락으로 종료했다. Crashpad의 `posix_spawn` 실패는 두 실행에서 별도로 관찰됐다.

## 범위와 성공 기준

- 브라우저 샌드박스 구현과 Chrome의 **하드웨어 GPU 가속**은 이번 범위 밖이다. `--no-sandbox --disable-gpu`는 외부 네트워크를 차단한 일회용 KVM 시험 이미지에만 넣는다. (2026-11-21 갱신: 사용자 승인으로 제품 매니페스트에도 임시 `--no-sandbox`가 들어갔다. `apps/chrome/README.md` 참조.) 서명 정책·기본 런처는 바꾸지 않는다. 콘텐츠는 로컬 테스트 페이지만 사용한다.
- 기존 RustOS Wayland/디스플레이 DVM은 유지한다. Chrome GPU 프로세스가 소프트웨어 경로에서도 만들어질 수 있으므로, 프로세스 이름이 아니라 실제 렌더링 방식과 프레임 표시를 확인한다. GPU 장치를 가짜로 광고하거나 DRM 오류를 성공으로 바꾸지 않는다.
- 완료 기준은 **브라우저 창 표시 → 로컬 페이지 렌더링 → 탭 생성·입력 → 정상 종료 → 동일 디스크 재부팅 후 프로필 상태 유지**다. 서비스 준비, Chrome PID 생성, `about:blank` 생존은 각각 중간 증거다.

## 1. Qt Wayland 런타임과 첫 프레임

- `xtask` 스테이징에서 Chrome이 로드한 Qt 메이저 버전과 플러그인 탐색 경로를 확인한다. 해당 Qt와 ABI가 맞는 Wayland QPA 플랫폼 플러그인과 전이 의존성을 [기존 런타임 잠금·검증](abi/prebuilt-runtime.md)에 넣는다. 실제 플러그인 경로와 `dlopen` 의존성을 검증하고, 호스트 라이브러리 fallback을 허용하지 않는다.
- 새 TmpFs 프로필로 기존 FAT 문제를 분리한다. `uiserver`의 Wayland 연결, xdg-shell configure/ack, 실제 소프트웨어 버퍼 제출을 확인한다. 프로토콜 실패가 나오면 Chrome 초기화 오류와 구분해 필요한 Wayland 동작만 보완한다. 하드웨어 DRM/GBM 지원을 이 단계의 전제로 삼지 않는다.
- **통과:** 동일한 게스트 프로필에서 Qt 플러그인 로드, Chrome 창 최초 표시, 알려진 로컬 페이지의 제목과 픽셀, 탭 하나 열기·입력을 확인한다. Chrome의 창·버퍼 증거를 다른 Wayland 클라이언트나 단순 PID 로그로 대체하지 않는다.

## 2. 영구 프로필을 지원하는 POSIX 데이터 볼륨

- FAT 부팅 볼륨과 기존 사용자 디스크는 그대로 둔다. [저장소 계획](large-file-io-plan.md#ext4)에 따라 **별도 ext4 RW 데이터 볼륨**을 vfsd의 `FsVolume` 뒤에 구현한다. 승인된 파일시스템 형식과 기능 범위만 마운트하고, 기존 FAT `/data`를 암묵적으로 변환하거나 덮어쓰지 않는다.
- 첫 완결 범위는 심볼릭 링크, 원자적 rename, 열린 파일의 unlink 수명, advisory lock, 공유 파일 매핑·동기화, `fsync`/디렉터리 지속성이다. 안정적인 inode/볼륨 식별자와 장애 후 메타데이터 회복을 검증한다. ext4 RW로 광고하기 전에 지원하는 기능 비트와 저널 복구 범위를 명시한다. 복구가 필요한 볼륨은 복구 기능이 준비되기 전까지 쓰기 마운트를 거부한다.
- **통과:** 새 영구 디스크로 Chrome 첫 실행, 두 번째 실행의 Singleton 동작, 정상 종료 후 재부팅, 로컬 사이트 상태와 프로필 파일의 재사용을 검증한다. 일회용 디스크에서 쓰기 중 중단·복구와 `fsck`도 별도로 검증한다. FAT 위에 가짜 링크 파일을 만들거나 프로필 전체를 TmpFs로 옮기는 것은 영구 해결책이 아니다.

## 3. `posix_spawn` / `vfork` 수명 구현

- `procd`는 허용할 프로세스 생성 조합과 각 인수의 정책을 소유한다. Ring 0은 `vfork`, legacy `clone` 및 `clone3`의 glibc spawn 조합을 하나의 공유 주소공간 수명 경로에 연결한다. 일반 `fork`와 `pthread_create`의 기존 의미는 바꾸지 않는다.
- 새 프로세스와 주소공간 공유를 별도로 표현한다. **호출한 부모 스레드**만 실제 자식 `exec` 커밋 또는 종료까지 기다리고, 실패한 `exec`는 일찍 풀어주지 않는다. glibc가 쓰는 초기 자식 스택, 지원되는 clone3의 `CLONE_CLEAR_SIGHAND`, 실패 전달을 보존한다. 자식 종료·신호·부모 종료·준비 중 롤백 시 공유 MM 참조와 대기권을 정확히 한 번 정리한다. COW `fork`로 이름만 대체하지 않는다.
- **통과:** 게스트 glibc `posix_spawn`으로 정상 실행, 존재하지 않는 실행 파일의 errno, spawn 파일 액션, 멀티스레드 부모, 즉시 종료/신호 경합을 검증한다. 이후 실제 Chrome에서 Crashpad 핸들러 `exec`와 초기화를 확인한다. 크래시 덤프 분석이나 `ptrace` 전체 지원은 spawn 성공과 별도다.

## 4. 후속 호환성: 실제 호출과 실패로 범위 확정

| 항목 | 계획 | 완료 판정 |
| --- | --- | --- |
| `inotify` | 관찰된 미구현. vfsd가 inode·마운트 수명에 맞춰 감시를 소유하고 성공한 namespace 변경 이후 이벤트를 발행한다. rename 쌍, watch 제거, 큐 초과, nonblocking read와 poll/epoll을 하나의 경로로 검증한다. | 게스트 파일 감시 회귀와 Chrome 또는 Qt의 실제 감시 기능 성공. |
| D-Bus | 현재 시스템 버스 소켓이 없다. 어떤 Chromium 기능이 어떤 버스를 실제로 필요로 하는지 재추적한다. 필요하면 표준 D-Bus 구현을 Ring 3 서비스로 스테이징하고 정규 Unix 소켓·피어 자격 증명·서비스 수명으로 연결한다. 시스템 버스와 세션 버스는 별도다. | 버스 인증·왕복, 그 버스를 쓰는 기능 성공. 로그를 숨기거나 가짜 버스 소켓을 만들지 않는다. |
| 나머지 ABI | 첫 프레임 이후 실패를 다시 추적한다. `timerfd`, `pidfd`, `waitid` 등은 호출과 사용자 영향이 확인될 때 우선 구현한다. 단순 ENOSYS 탐색은 완료 차단으로 간주하지 않는다. | 각 추가 항목에 Linux 비교와 게스트 기능 회귀가 있다. |

## 검증 순서

1. **Qt와 실제 첫 프레임이 먼저.** 영구 저장소와 spawn은 독립 작업으로 진행할 수 있지만 Qt를 고치기 전에는 추가 UI 실패를 추측하지 않는다.
2. 각 구현 배치에서 `cargo xtask dev-plan`, `cargo xtask check`, 해당 패키지 테스트, 1 vCPU Chrome 게스트 시험을 실행한다. [기존 `chromeprobe`](chrome-gap-fs-net.md#acceptance-not-yet-complete)는 호환성 회귀로 유지하되 실제 Chrome 성공 표식과 분리한다.
3. 합친 뒤에는 1·8 vCPU에서 같은 로컬 페이지를 시험한다. 영구 프로필은 두 번 부팅한 증거를 남기고, `vfork`/파일시스템 변경은 실패·복구 사례와 formal PR 게이트를 함께 검증한다. (2026-11-25 기준: 1단계 Chrome 창 표시·입력 60초 유지와 `chromeprobe` 505/505 통과가 검증되었으며, 2단계 ext4 RW 데이터 볼륨과 3단계 공유 주소공간 `vfork` 및 영구 프로필 재부팅 검증은 미완료 상태다.)
